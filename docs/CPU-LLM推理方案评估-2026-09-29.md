# CPU 上的 LLM 推理方案与 fast-router 适配性评估

## 结论先行

> **CPU 推理有有效方案，但不存在一个“换引擎后，9B 通用模型立刻又快又准”的普适解。**
>
> CPU 适合小模型、低并发、短上下文、窄任务。fast-router 的方向不应只盯着通用 9B：专用 64M scorer 已在当前 30 条基准上达到 73.3%，同一基准约 2.6 秒；而 322M Laya CPU 实测更快（约 1.5–2 秒），但同一任务集 P1 只有 56.7%。对必须同步小于 1 秒的场景，当前有效方案是异步路由/缓存或硬件加速，不是单纯换 CPU 推理框架。

**置信边界**：以上 P1 是当前小样本/合成分布实验，不代表生产流量泛化；该 64M 模型的训练标签来自手写规则，不是 9B 教师蒸馏。

### 方法

将方案分为三类比较：

1. **同一个大模型换运行时**：llama.cpp 与面向 Intel CPU 的 OpenVINO。
2. **同一运行时优化执行**：量化、线程/批处理调优、prompt/KV 复用。
3. **改变任务模型**：面向任务路由训练小模型，或使用专用判别/决策模型。

按四个成功维度评估：决策准确率、当前请求延迟、端到端延迟、部署/维护成本；并检查主要失败方式和回退路径。

## 二、为什么 CPU 上“大模型推理感觉不好”

### 1. 单请求生成的 decode 常受内存搬运限制

自回归生成每一步都要读取大量模型权重；低并发 CPU 场景下，算力并不会自动转成高 token/s。量化减少权重体积和内存搬运，SIMD/矩阵指令能加速 kernel，但它们没有消除“每一步仍需读取模型权重”的基本成本。批量请求可以摊销权重读取，但交互式路由往往是 batch=1。

该结论是通用机理，不可直接推导某台设备的 token/s；设备内存带宽、CPU 指令集、模型架构、上下文长度和线程配置都会改变实测结果。

### 2. 路由 scorer 把重复 prefill 成本放大

当前 Jev 路径不是普通的一次短回答：多个 task 类别需要逐候选进行 yes/no scoring。若候选问题前缀重复而不复用 KV，每个候选都会重新处理大段共同输入。项目已经实现批量 KV 复用，9B benchmark 从污染期历史数字修复后实测约 2.1–3.9x 加速；收益仍受共享前缀比例约束。

### 3. 量化主要改善速度/内存，不会凭空缩短任务决策链

Q4 可以显著缩小权重并提高 CPU 运行可行性，但更低 bit 通常引入精度/能力风险。量化格式须按**本任务 P1**验证，而不能只看 perplexity 或模型能否加载。已经是 Q4 的 9B 仍然很慢，说明对这个特定任务继续压 bit 不是可靠的亚秒解。

### 4. “换框架”可以优化实现，但不自动改变模型计算量级

llama.cpp 支持多种 CPU SIMD/量化路径；当前上游还提供了 **llama.cpp OpenVINO backend，可让 GGUF 经 OpenVINO 在 Intel CPU/GPU/NPU 上执行**。但官方目前说明构建路径针对 Linux/Windows，验证重点是 Core Ultra Series 1/2；量化模型精度和性能优化仍在进行中。官方验证表里 Qwen3.5 9B 的 CPU stateless 通过、stateful 未通过。fast-router 的批量 KV 复用使用有状态序列，因此不能把 OpenVINO backend 当成可直接替换的后端。另有 OpenVINO GenAI 的 Optimum 导出路径，通常会把 Hugging Face 模型导出成 OpenVINO 格式并做 INT4 压缩；这不是 llama.cpp GGUF 后端，不能把两条路线混为一谈。

若仍运行同一 9B 模型、相同 prompt 与相同候选数，runtime 优化可能有收益，但未在本机测得之前不能承诺数量级提升。

## 三、方案矩阵

| 方案 | CPU 延迟潜力 | 任务质量风险 | fast-router 判断 |
|---|---|---|---|
| llama.cpp + 当前 9B Q4 | 已有实测，但慢 | 当前 30 条 P1=73.3%；统计区间宽 | 保留质量基线；继续使用 KV 前缀复用，不把它当亚秒方案 |
| llama.cpp 调优（线程、CPU ISA、prefill batch、亲和性） | 低到中，需设备实测 | 不改模型时风险低 | 值得做一次参数 sweep；不要凭逻辑核心数猜最佳线程 |
| 继续压低量化位宽（Q3/Q2） | 可能更省带宽/内存 | 较高，必须重验 P1 | 仅做实验矩阵，不默认升级 |
| llama.cpp OpenVINO backend + GGUF | Intel CPU 上值得 benchmark；可保留 GGUF | 官方构建路径目前针对 Linux/Windows；验证重点 Core Ultra 1/2；Qwen3.5 9B stateful CPU 路径未通过 | 不能直接替换当前批量 KV scorer；适合另建 stateless/Linux 对照 POC，非当前 Mac 直接方案 |
| OpenVINO GenAI + INT4 导出 | Intel CPU 上值得作为独立 benchmark | 需导出/转换模型并验证模板与数值行为；不是直接加载 GGUF | 有 Hugging Face 原始权重时再评；部署/转换成本高于 llama.cpp OpenVINO backend |
| Laya 322M CPU | 本机约 1.5–2 秒/样本 | 已测 P1=56.7%，未过项目门槛 | 证明小型判别路线很快，但该 checkpoint 当前不合格 |
| 64M 专用 scorer | 同一 30 条实验的 10 前向约 2.6 秒；fast 首评记录约 2.77 秒 | 同一测试集 P1=73.3%；训练/测试模板相关，和 9B 错误模式不一致 | 当前最有希望的 CPU 路线；作为候选/实验模型，需真实流量、冻结集和扩大样本复核 |
| 异步首评 + session 路由缓存 | 当前请求可不等待慢评分；后续轮复用 | 首轮走 hint/fast route，语义可能不同 | 已验证的交互延迟解，不是让 9B 算得更快 |
| Apple Silicon Metal/Core ML/MLX 等加速 | 在支持设备上可能有大幅收益 | 算法/模型路径要同集复测 | 硬件条件变化时重跑；不能外推到当前 Intel x64 Mac |
| 额外服务/sidecar | 取决于底层设备与模型 | 协议兼容不代表算法等价 | 若仍跑 CPU，换成 sidecar 不会自动消除计算瓶颈 |

## 四、fast-router 上最有效的实际策略

### A. 低风险：对当前 llama.cpp 配置做可复现调参

固定模型文件、量化、prompt、候选数、上下文和硬件，测：

- `llama-bench` 的 prompt processing（PP）与 token generation（TG）；
- 物理核线程数周围的线程 sweep，而非直接用逻辑核心数；
- 独立调 generation 与 batch/prompt 线程；
- 批大小、量化格式、模型加载冷/热启动；
- 路由 scorer 的整条路径（包含模板应用、10 个候选、KV 复用、JSON/HTTP 开销）。

判断标准是 fast-router 的**每个 new-task 决策延迟和 P1**，不能拿通用聊天的 tokens/s 替代。

### B. 高收益：保持决策任务窄，使用专用小模型

项目已有结果说明窄域 scorer 可以小型化；但 64M 的 73.3% 不是生产质量结论。推荐把它作为 fast tier candidate：

1. 用独立的 300+ 样本冻结评估集，覆盖真实任务和边界混淆；
2. 同时测 64M、9B、Laya、hint/default baseline；
3. 报 macro-F1、混淆矩阵、P50/P95 评分延迟和错误类别；
4. 在真实流量先 shadow，不立即替换主路由；
5. 质量过门后再做小流量 session A/B。

### C. 要求“请求响应立即返回”：利用架构，而非同步等待大模型

如果产品目标是首请求 P2<1s，而不是“首个请求必须等 Jev 完成”，异步首评、hint 即走、后台评分、同一 session 后续轮继承结果，通常比把 9B CPU 再压一点更稳、更可逆。需要分别报告“网关响应延迟”和“后台决策完成延迟”。

### D. 要求同步 Jev 决策：先减计算，再换 runtime

依次尝试：

1. 64M/更小的本域专用 scorer；
2. 精简候选或采用分层分类（前置小分类器 + 难例交给 9B）；
3. 共享前缀 KV cache，避免每候选重复 prefill；
4. 线程/CPU ISA/量化参数实测；
5. 再评估 OpenVINO 或目标硬件专用后端。

每次改变 scoring 算法、prompt 或量化都要重跑 P1 冻结集。

## 五、按硬件的建议

| 设备 | 优先顺序 |
|---|---|
| 当前 Intel x64 Mac（i7-9750H / 无已启用的 llama.cpp GPU 后端） | 64M 专用 CPU scorer → llama.cpp 参数 sweep → 若有 Linux/Windows Intel 测试环境，再对照 OpenVINO backend；官方文档没有给出 macOS 构建路径 |
| 新款 Intel CPU/带 AMX 的 Xeon | llama.cpp 与 OpenVINO GenAI+INT4 同机 A/B；按是否支持目标模型/导出格式选 |
| Apple Silicon | 优先验证 Metal/Core ML/MLX 等硬件路径；CPU 仅作 fallback |
| 有 CUDA GPU 的 Linux/Windows | GPU 推理通常优先；CPU 量化用于 fallback 或小流量并发，不以 CPU-only 假设调优 |
| 低功耗 ARM SBC | 小型专用模型、INT8/INT4 与系统 NPU 优先；大 dense LLM 不应作为低延迟默认项 |

硬件表是筛选实验的顺序建议，不是性能保证。

## 六、DecisionRecord

| 预测 | 结果/证据 | Surprise 或边界 |
|---|---|---|
| 存在适合 CPU 的开源推理引擎 | llama.cpp、OpenVINO CPU 路径均存在 | 有引擎不等于当前模型/接口能直接接入 |
| 换引擎即可解决当前 9B CPU 延迟 | 当前引擎评估显示 sidecar 仍跑同类 CPU 计算 | 不成立；模型大小、重复候选 prefill 和硬件更关键 |
| 更小模型一定够准 | Laya 更快但 P1 56.7%；64M 结果与 9B 错误基本互补 | 不成立；速度和决策质量必须独立验收 |
| 64M 是当前最佳 CPU 路线 | 30 条集上 P1=73.3%、10 前向约 2.6 秒 | **candidate**：统计功效有限，且训练标签为规则生成，不是 9B 蒸馏 |
| 同步调用 9B 能通过参数调优达到亚秒 | 无本机证据支持 | 不成立前不可承诺；先做 benchmark sweep |

## 七、局限

1. 公开运行时文档只证明功能/支持范围，不证明在本机的相对性能。
2. 本地模型延迟来自项目历史实验，硬件/构建参数/冷热启动差异会影响复现。
3. fast-router 的 30 样本 P1 置信区间很宽；不能用来宣称 64M 与 9B 等价。
4. 当前未在本机实测 OpenVINO 同模型、同 prompt、同任务集，也未验证模型转换后 yes/no logits 等价。
5. 线程调优、量化压缩、框架转换都应保留原模型 baseline 及回滚配置。

## 八、结论

CPU 推理并非“没有好方案”，而是要把“好”限定在任务和硬件上：

- **通用 9B CPU + 同步多候选决策**：当前硬件上不适合做低延迟首评；换引擎可能优化常数，不保证根治。
- **窄域路由决策**：专用小模型、减少重复 prefill、KV 复用，是比单纯换框架更直接的路线；64M 已值得进入真实分布验证，但尚不能定为生产默认。
- **低延迟产品体验**：异步首评和路由缓存已经比等待 9B 完成更可靠；若必须同步且高质量，目标设备需要可用的 GPU/NPU/高速统一内存。
