# Jev 路由决策效果评估

## 结论先行

> 当前日志可以回答“请求是否成功返回”和“路由结果如何分布”，不能单独回答“Jev 是否判对了任务类型”或“选中的模型是否优于其他候选模型”。

评估必须拆成四层：

1. **采集层**：日志是否完整、可关联、无污染。
2. **运行层**：路由是否降低错误、延迟和成本。
3. **决策层**：Jev 的 task code 是否正确，置信度是否可信。
4. **因果层**：被选模型是否真的优于 baseline/其他候选模型。

没有人工标签、客户端成功信号或对照实验时，最多只能报告运行代理指标，不能把 `HTTP 2xx` 叫作 Jev 决策正确。

## 一、来源与方法

### 来源

| 来源 | 可观察内容 |
|---|---|
| `router/verdict.go` | `session/task_turn/task_code/model_id/upstream/route_via/status/outcome` |
| `router/gateway.go` | 请求转发结果写入 verdict；`fast/slow` scorer 写入 `train_log` |
| `router/scorer.go` | Jev choice、概率分布、confidence |
| `data/verdicts.jsonl` | 当前运行样本；现有样本为 `connect_error`，不足以评估质量 |
| `docs/fast-router-自进化评估-2026-09-28.md` | 当前 L1 校准的反馈偏置和代理指标边界 |

### 方法

对日志字段逐一映射到“预测、执行、结果、真值”四类证据，并按维度/死法/可逆性检查：

- **维度**：决策准确性、路由收益、稳定性、覆盖率、校准度。
- **死法**：把网络成功当任务成功；把继承路由当新样本；被选模型自我强化；错误把 429/鉴权/断连归因给模型。
- **可逆性**：先离线报表和 shadow/canary，再影响生产选择；清空 measured/verdicts 可回到冷启动。

## 二、当前日志能证明什么

### `verdicts.jsonl` 能证明

- 某次路由最终走了哪个 `model_id/upstream`。
- 路由来自 `jev`、`fast`、`hint`、`strong-hint` 还是 `inherit`。
- 请求是否连接失败、收到上游错误或得到 HTTP `<400` 响应。
- 每个 `(task_code, model_id)` 的粗粒度 `ok_rate`，用于当前 L1 measured 校准。
- 任务类别覆盖是否存在空层。

### `verdicts.jsonl` 不能证明

- `task_code` 是否符合用户真实意图。
- 返回内容是否解决了任务。
- 被选模型是否比未选模型更好。
- 2xx 响应是否包含正确代码、正确 JSON、正确工具调用或可执行结果。
- 失败是模型质量、请求参数、鉴权、限流、配额、上游故障还是网络问题。

### `train_log.jsonl` 能证明

- `fast` 与 `slow` scorer 对同一 `state` 的预测、置信度和时间顺序。
- fast/slow 分歧率，以及模型替换前后的预测漂移。

它仍然不是外部真值：slow tier 是当前教师/评估器，不自动等于用户任务成功。

## 三、四层指标

### 1. 采集层：先确认日志可信

| 指标 | 计算 | 通过条件 |
|---|---|---|
| 关联完整率 | 有 request/session/decision 关联 ID 的事件 ÷ 总请求 | 目标 ≥99.9% |
| 决策落盘率 | 有路由事件且有终态结果的请求 ÷ 总请求 | 目标 ≥99% |
| 字段完整率 | `task_code/model_id/via/status/outcome` 非空比例 | 新任务 `task_code`、模型、via 必须非空 |
| 重复率 | 同一 request/attempt 被重复计数的比例 | 需要接近 0 |
| 隐私合规率 | 原文、API key、Authorization 等敏感数据泄漏数 | 0；`train_log` 原文必须有保留期/脱敏策略 |

当前缺口：`VerdictEvent` 没有 request ID、路由耗时、端到端耗时、模型版本、输入长度和错误分类，无法可靠做请求级 join。

### 2. 运行层：评估“路由后是否更稳、更快、更便宜”

按 `route_via × task_code × model_id × protocol × 时间窗口` 分组：

- **成功率**：仅作为运行代理，不作为语义正确率。
- **错误率**：按 `connect_error`、4xx、429、5xx、超时分层。
- **延迟**：路由耗时、首 token、总耗时的 p50/p95/p99。
- **成本**：输入/输出 token 和实际价格。
- **重试率**：客户端或网关重试次数。
- **继承稳定性**：同一 session 的 `inherit` 是否复用成功，不能当作新的 Jev 分类样本。

当前 `outcome == "ok"` 只是 HTTP status `<400`。它适合做“可用性信号”，不适合叫“任务通过率”。

### 3. 决策层：评估 Jev task code

必须引入独立真值 `label_task_code`，来源按可信度排序：

1. 用户显式反馈或任务完成状态；
2. 工具/测试/编译器的客观结果；
3. 人工盲标；
4. 独立教师模型复核；
5. 当前 Jev 自己的重复评分（只能测稳定性，不能当真值）。

核心指标：

- accuracy、macro-F1、每类 precision/recall；
- confusion matrix，重点看 C 吸引 A/B/I/J 等已知吸引子；
- `confidence` 分桶后的准确率；
- Brier score / ECE，判断 confidence 是否可用于降级；
- 低置信度 abstain 后的覆盖率-准确率曲线；
- fast vs slow disagreement rate、按类别的分歧矩阵。

统计要求：

- 新版本/新策略必须使用冻结测试集；
- 生产日志只能做外部分布测试，不能替代冻结集；
- 每个主要结论报告样本量和置信区间；
- 30 条样本的 ±15pp 级别误差不能用来宣称小幅提升。

### 4. 因果层：评估“Jev 选模型是否带来收益”

只观察实际被选模型会产生选择偏差：未被选模型没有结果，不能比较。

优先级：

1. **离线 replay**：固定同一批 state，用候选路由器和 baseline 重新评分。
2. **shadow**：真实请求仍走当前模型，同时把候选模型只做评估，不把结果返回用户。
3. **小流量 A/B**：按 session 随机分配 Jev、默认模型、成本优先或人工 hint。
4. **交错实验**：同类请求在可接受成本内轮换候选模型。

因果指标：

```text
quality_lift = quality(jev) - quality(baseline)
latency_delta = latency(jev) - latency(baseline)
cost_delta = cost(jev) - cost(baseline)
regret = quality(best_eligible_model) - quality(chosen_model)
```

质量函数必须预先定义，例如：

- 代码任务：测试通过率/编译通过率；
- 结构化抽取：schema 校验率/字段 F1；
- 工具任务：工具调用成功率/最终任务完成率；
- 翻译：人工或基准集质量；
- 普通问答：人工评分或独立评审。

## 四、当前实现的关键陷阱

### 1. `inherit` 会重复放大样本

工具循环的 continuation 会复用上一次路由。若把每个 `inherit` 事件当作新的 Jev 决策，会把一个新任务重复计权，导致某个模型的 `ok_rate` 被会话长度影响。

报表应同时输出：

- **request-level**：每个 HTTP 请求的运行结果；
- **new-task-level**：每个 `TaskTurn == "new"` 的首次 Jev 决策；
- **session-level**：整条工具链最终是否完成。

L1 校准至少应优先使用 `new` 任务事件，或按 session 对 continuation 去重。

### 2. `connect_error` 排除是对的，但错误分类还不够

当前 `Calibrated()` 排除 `connect_error`，但把所有 `upstream_error` 视为模型失败。以下错误不应直接归因于模型：

- 401/403：鉴权或配置；
- 404：endpoint/model 配置；
- 408/429：超时、限流或配额；
- 500/502/503：服务端或网关故障；
- schema/工具调用错误：可能是协议转换或请求构造问题。

建议增加：

```text
error_class = transport | auth | rate_limit | request | provider | model_quality | unknown
```

只有 `model_quality` 或经过规则确认的请求错误，才进入模型 measured。

### 3. 当前 selector 反馈是“使用偏置”的

`Select()` 只在实际选中的模型上积累结果；越早被选中的模型越容易获得样本，可能形成：

```text
被选中 → 获得更多样本 → measured 更稳定 → 更容易继续被选中
```

在没有 shadow 或 epsilon 探索前，`ok_rate` 只能叫“被选中条件下的运行率”，不能叫“模型真实相对质量”。

## 五、推荐的最小落地顺序

### P0：先把现有日志变成可评估数据

在 `VerdictEvent` 增加：

```text
request_id
decision_id
route_started_at / route_finished_at
request_finished_at
model_version
input_tokens / output_tokens
error_class
http_status
latency_ms
baseline_model_id（若有 shadow/对照）
```

不要默认落盘完整 prompt；优先 `state_hash`、长度、脱敏摘要和可选加密原文。

### P1：建立第一版离线报表

按日/版本生成：

1. 采集完整率；
2. new-task 的 task code 分布和置信度分布；
3. fast/slow 分歧率；
4. `route_via × model × task` 的 HTTP 成功率和错误分类；
5. 继承链按 session 去重后的成功率；
6. 与默认路由的延迟/成本对比。

这一步只做观察，不改变路由。

### P2：建立真值和 baseline

- 采集 300+ 条冻结/人工复核样本；
- 为每条样本补 `label_task_code` 和任务质量结果；
- 固定 default、cheapest、Jev 三个 baseline；
- 输出 confusion matrix、macro-F1、quality lift、cost/latency delta。

### P3：小流量因果验证

- 先 shadow；
- 再 5%～10% session-level A/B；
- 设硬门：错误率、p95、成本、任务质量任一恶化即回滚；
- measured 只在验证通过后进入 active。


## 七、DecisionRecord

| 预测 | 实测/当前状态 | 判定 |
|---|---|---|
| 有了 verdict 日志就能判断 Jev 是否选对 | 只能判断 HTTP 级运行结果，没有 task 真值和候选对照 | **不成立** |
| `ok_rate` 可以直接作为模型质量 | 2xx 只代表协议/上游响应成功 | **不成立，降级为代理指标** |
| `train_log` 可以作为自训练质量证明 | 它记录 fast/slow 预测，slow 仍是教师，不是外部真值 | **不成立，先作为漂移/分歧数据** |
| 按 new-task、错误分类和 baseline 补齐后可评估 | 需要扩字段并进行 shadow/A-B | **candidate** |

## 八、局限与结论

### 局限

1. 当前仓库没有真实用户任务的独立质量标签。
2. 现有 `data/verdicts.jsonl` 样本极少，且示例是 `connect_error`，无法得出质量结论。
3. upstream HTTP 成功与最终任务成功之间存在明显间隔。
4. 没有 shadow/A-B 时无法估计未选模型的反事实结果。

### 结论

当前正确的评估口径是：

> **先用 verdicts 评估路由运行稳定性，再用独立 task label 评估 Jev 分类，再用 shadow/A-B 评估 Jev 选模的因果收益。**

在 P2 之前，禁止使用以下表述：

- “Jev 准确率 = `ok_rate`”
- “模型被选中次数多，所以更好”
- “fast 与 slow 一致，所以正确”
- “HTTP 2xx 证明任务完成”
